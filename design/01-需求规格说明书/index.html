    01 需求规格说明书¶

    版本：v1.0 ｜ 日期：2026-09-11 ｜ 状态：评审稿

    1. 项目背景与目标¶

    1.1 背景¶

    人工代码评审存在三个痛点：慢（一个中型项目初评动辄数人日）、浅（评审者难以追踪每个跨文件调用链）、不稳定（问题发现质量依赖个人经验）。现有静态分析工具（SonarQube、ruff、ESLint）规则固定、误报多、无法理解业务语义。LLM 具备语义理解能力，但直接"整库丢给大模型"会遭遇上下文限制、幻觉和高成本。

    本项目用一个 Agent 来解决：以 GLM-5.3 Flash 为推理核心，配一组代码库操作工具（读写、搜索、符号跳转、执行），让模型像人类评审员一样"带着工具看代码"，实现可验证、可解释的代码库级审计。

    1.2 项目目标¶

    目标 量化描述
    G1 自动检测 对输入代码库输出 Bug / 性能 / 规范三类问题清单，critical+high 级别精确率 ≥ 85%
    G2 自动修复 对 critical/high 问题生成修复 Patch，沙箱验证通过率 ≥ 60%，验证通过的标记为 verified
    G3 自动测试 对被修复函数生成可运行单测，沙箱运行通过后收录，收录用例通过率 100%（不通过即剔除）
    G4 审计效率 千行代码端到端审计耗时 < 30s（P50）；整体效率较人工初评提升 70%+
    G5 可解释性 每条问题附带文件/行号/代码片段/跨文件证据链/置信度，报告人可直接定位

    1.3 用户与使用场景¶

    • 个人开发者：提交/接手项目前跑一次"代码体检"。
    • 团队 Tech Lead：代码评审的前置粗筛，把人力聚焦到架构与业务问题上。
    • 求职者/学生：审计自己的课程设计或开源贡献，演示 AI 工程能力。

    2. 功能需求（FR）¶

    FR-1 项目接入¶

    编号 需求 验收标准
    FR-1.1 支持本地文件夹路径（CLI/API）与 zip 包上传（Web） 两种入口产出一致的工作副本
    FR-1.2 语言识别：按扩展名统计 + 内容启发式，输出主语言与语言分布 识别准确率 > 95%（常见项目）
    FR-1.3 文件过滤：自动忽略 .git、node_modules、venv、__pycache__、构建产物、二进制、超天文件；遵循 .gitignore 过滤后清单人工抽查无误
    FR-1.4 规模保护：单次审计 ≤ 2000 文件 / 50 万行；超出提示分批或按模块选择 超限时报明确错误而非卡死
    FR-1.5 编码容错：GBK/UTF-8/带 BOM 自动探测，解码失败文件记录并跳过 不因单个文件编码崩溃

    首期语言范围：Python 完整闭环（检测/修复/单测），JavaScript/TypeScript 支持检测与报告（修复与单测降级为建议输出）。架构上语言能力插件化（解析器、规则库、测试执行器三件套按语言注册），预留 Java/Go 接入点。

    FR-2 代码库理解¶

    编号 需求 说明
    FR-2.1 全库 AST 解析 tree-sitter 解析每个源文件，提取函数/类/方法定义、导入、全局常量，形成符号表
    FR-2.2 依赖与调用图 imports 精确建边；函数调用同文件精确匹配、跨文件按符号表解析（含 from x import y 别名）
    FR-2.3 架构摘要 分模块 LLM 摘要（map）→ 全局汇总（reduce），产出"架构卡片"：技术栈、目录职责、入口、核心数据流、风险热点
    FR-2.4 索引持久化 符号表/调用图写入 SQLite，支持增量（文件 hash 未变则复用上次解析）

    FR-3 问题检测（核心）¶

    问题分类学与严重级别定义：

    三类问题 × 四级严重度：

    类别 典型检测项（首期规则库 ≥ 40 条，持续扩充）
    Bug / 正确性 未定义/未使用变量、空值解引用、except: pass 吞异常、资源未关闭（文件/连接）、可变默认参数、== None、边界差一、异步未 await、类型混用、不可达代码
    性能 循环内重复 IO/网络调用、N+1 查询模式、用 list 做 in 成员判断（应 set/dict）、循环内重复不变计算、字符串 += 拼接大循环、全局大对象反复深拷贝、无 timeout 的网络请求
    规范 / 可维护性 函数超 80 行、圈复杂度超 15、重复代码块（≥6 行）、魔法数字、命名不规范、硬编码配置/密钥、缺失类型标注（Python）、过深嵌套（≥4 层）
    安全（加分项） SQL 拼接、eval/exec、命令注入（os.system 拼用户输入）、硬编码密钥（正则+熵检测）、不安全反序列化（pickle.loads 外部数据）

    严重级别：critical（必致错误/安全漏洞） > high（大概率缺陷/显著性能） > medium（可维护性） > low（风格）。

    每条 Issue 必须包含：id、category、severity、title、file、line_start/line_end、code_snippet、description（人话解释为什么是问题）、evidence（跨文件调用链等证据）、suggestion（修复建议文字）、confidence（0~1）、source（rule / llm / rule+llm）。

    编号 需求 验收标准
    FR-3.1 静态规则通道：AST 模式 + 正则规则全库扫描，零 LLM 成本 全量文件覆盖，单规则可配置开关
    FR-3.2 LLM 审查通道：按文件（函数级切片）审查，规则命中作为 hint 注入 每个源文件至少被 LLM 看过一次（预算内）
    FR-3.3 Agent 验证：对候选问题调用工具跨文件取证，剔除误报 误报剔除记录留痕（验证了什么、结论）
    FR-3.4 行号真实性校验：报告中行号必须落在真实文件行范围内 行号校验器 100% 拦截越界引用

    FR-4 修复生成¶

    编号 需求 验收标准
    FR-4.1 对 critical/high 生成 unified diff 格式 Patch Patch 语法可被 git apply --check 接受
    FR-4.2 沙箱应用 Patch 后运行项目现有测试（检测到 pytest/jest 则执行） 现测全绿 → verified；现测挂 → 回滚并标记 needs-review
    FR-4.3 无测试的项目：Patch 仅做语法检查（AST 可重新解析）+ 标记待人工确认 不夸大验证状态
    FR-4.4 应用方式：写回文件 / 导出 .patch 文件两种，默认导出（不静默改用户代码） 默认行为安全

    FR-5 单元测试生成¶

    编号 需求 验收标准
    FR-5.1 默认对"被修复的函数"生成回归测试；支持指定函数/文件批量生成 覆盖修复点
    FR-5.2 Python 生成 pytest 用例（含正常路径/边界/异常三类断言） 用例含有效 assert（非空跑）
    FR-5.3 沙箱运行生成用例，失败自动带着报错信息重试 ≤ 2 次，仍失败则丢弃该用例 收录用例 100% 可跑通
    FR-5.4 测试文件输出到 tests/generated/，不污染用户已有测试 可一键删除

    FR-6 审计报告¶

    编号 需求
    FR-6.1 双格式输出：report.json（机器可读，含全部结构化数据）+ report.md / report.html（人读，含代码高亮）
    FR-6.2 报告结构：项目概览（规模/语言分布/技术栈）→ 健康分（0-100，按问题密度与严重度加权）→ 问题总表（按严重度/文件分组，可筛选）→ 架构摘要 → Top 修复建议 → 测试生成结果 → 耗时与 token 成本统计
    FR-6.3 健康分公式：100 - Σ(severity_weight × count) / KLOC × 归一化系数，权重 critical=10/high=5/medium=2/low=0.5，系数在 bench 中标定
    FR-6.4 支持基线对比：同一项目两次审计输出 diff（新增/已修复问题）

    FR-7 交互入口¶

    编号 入口 关键行为
    FR-7.1 CLI codeaudit run <path> --lang python --fix --tests --out report/ --verbose；进度条 + 阶段日志
    FR-7.2 REST API POST /api/audits（创建异步任务）、GET /api/audits/{id}（状态/结果）、GET /api/audits/{id}/events（SSE 实时进度流）、GET /api/audits/{id}/report?format=md
    FR-7.3 Web 演示 上传 zip 或填路径 → 阶段进度可视化（索引 n 文件 / 审查 m 文件 / 发现 k 问题）→ 在线报告查看（问题卡片、代码高亮、diff 视图）→ 下载报告

    3. 非功能需求（NFR）¶

    3.1 性能（对应"千行 < 30s"）¶

    编号 指标 目标 测量口径
    NFR-1 端到端审计耗时 P50 < 30s / 千行源代码 从 Ingest 开始到 Report 落盘为止（含全部 LLM 调用），统计 ≥ 10 个项目取 P50；千行=过滤后源代码行数
    NFR-2 LLM 并发 文件级并发 ≥ 8（信号量可配），且遵守 API 限流 压测无 429 失败
    NFR-3 增量审计 文件未变的重复审计，该文件零 LLM 调用 二次审计耗时 < 首次 40%

    3.2 质量（对应"精确率 85%"）¶

    编号 指标 目标 定义
    NFR-4 精确率 Precision critical+high ≥ 85% 报告的 critical+high 问题中，经人工标注确认为真实问题的比例（口径详见 04 文档）
    NFR-5 召回率 Recall ≥ 60%（金标集上） 报告问题覆盖金标问题的比例。简历话术用"准确率 85%"指 Precision，内部同时追踪 Recall 防止"少报多准"
    NFR-6 修复可用率 人工判定"可直接采纳或小改可用"≥ 60% 抽样 30 个 Patch 人工评分
    NFR-7 单测有效率 收录用例 100% 沙箱通过；含有效断言 ≥ 90% 有效断言=断言值与被测函数语义相关（抽样人评）

    3.3 稳定性与成本¶

    编号 需求
    NFR-8 LLM 调用失败：指数退避重试 ≤ 3 次；单文件审查失败不中断全局（降级记 warning）
    NFR-9 成本上限：单次审计 token 预算可配置（默认 200 万 token），超预算自动降级（跳过 low 优先级文件的 LLM 深审，只保留规则结果）
    NFR-10 Agent 防失控：单文件审查最多 25 次工具迭代；全局预算熔断；所有工具调用有超时

    3.4 安全¶

    编号 需求
    NFR-11 代码仅发送至 LLM API（用户自己的 key），不落第三方；报告不含密钥明文（检测到的硬编码密钥做打码）
    NFR-12 沙箱执行：子进程超时 60s、禁网（可选）、临时目录隔离；生成的测试代码执行前不做任何系统写操作之外的假设。生产部署建议换 Docker 沙箱（文档说明，非首期必做）

    4. 范围外（Non-goals，答辩时主动讲）¶

    1. 不做运行时插桩 / APM / 线上监控集成。
    2. 不做自动提交 PR / 合并到主干（只产出 Patch，应用权在用户）。
    3. 不承诺修复后代码 100% 语义正确——未验证的修复一律标 needs-review。
    4. 首期不做 IDE 插件（CLI + Web 已够演示与使用）。
    5. 首期不做跨仓库/微服务调用链分析（同库内为主）。

    5. 关键用户故事（验收剧本）¶

    US-1（主流程演示剧本，答辩直接用）： 1. 用户在 Web 端上传一个含 120 文件 / 2.4 万行的 Flask 项目 zip。 2. 40 秒内看到：架构卡片（"Flask + SQLAlchemy，三层结构，入口 app.py，核心业务在 services/"）。 3. 9 分钟后看到报告：健康分 68/100，critical 3（含一处 SQL 拼接注入）、high 11、medium 27、low 45；其中一条 high 展开了完整证据链：orders.py:88 调用 get_user() → users.py:41 可能返回 None → orders.py:89 直接访问 .id → AttributeError。 4. 点击"生成修复"：SQL 注入处给出参数化查询 Patch，沙箱跑通项目自带 14 个测试，标记 verified，并自动生成 4 条回归单测（全部通过）。 5. 下载 report.md 与 fix.patch、tests_generated/。

    US-2（增量场景）：同一项目改了 3 个文件后再次审计，仅重审变更文件，耗时 < 首次 40%。

    US-3（失控保护）：构造一个故意让 Agent 纠缠的巨型文件，验证 25 次迭代上限与预算熔断正常触发，任务以部分结果收尾而非挂死。
