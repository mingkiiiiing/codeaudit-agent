    02 系统架构设计¶

    版本：v1.0 ｜ 日期：2026-09-11

    1. 总体架构¶

    ┌────────────────────────────────────────────────────────────┐
│                接入层：CLI ｜ REST API ｜ Web UI             │
│                （SSE 进度流 / 报告查看 / Patch 下载）          │
├────────────────────────────────────────────────────────────┤
│         编排层 Audit Orchestrator（七阶段流水线状态机）        │
│   Ingest → Index → Understand → Detect → Fix → TestGen     │
│                                    → Report                │
├────────────────────────────────────────────────────────────┤
│              Agent 运行时（复用既有工具调用框架）              │
│    ReAct 循环：LLM ⇄ Tools；迭代上限 / token 预算 / 结构化停止  │
├────────────────────────────────────────────────────────────┤
│  工具层  fs │ code_search │ symbol_graph │ patch │ exec     │
│         （10 个工具，完整 Schema 见 03 文档）                 │
├────────────────────────────────────────────────────────────┤
│  基础设施层                                                  │
│  tree-sitter 解析器 │ SQLite 索引库 │ GLM 客户端（限流/重试/  │
│  缓存/token 计量）│ 沙箱执行器 │ 文件内容与结果缓存            │
└────────────────────────────────────────────────────────────┘

    核心决策：为什么是"静态规则 + LLM Agent"双通道，而不是单通道？

    方案 优点 致命缺陷
    纯静态规则（类 SonarQube） 快、免费、确定 误报高（无法理解语义）、无法发现逻辑/跨文件问题
    纯 LLM 扫 语义理解强 幻觉与误报不可控、贵、慢、漏报取决于注意力
    双通道 + Agent 验证 规则管"召回"，LLM 管"精确"，工具管"证据" 实现复杂度高（本项目核心工作量，也是亮点）

    数据流向：规则扫描结果以 hint 形式注入 LLM 审查 prompt（引导注意力、提供线索）；LLM 产出候选 Issue 后，由验证 Agent调用 find_references / get_symbol / read_file 等工具跨文件取证，能拿出证据链的才入库，拿不出的标低置信度或丢弃。这就是"85% 精确率"的架构来源。

    2. 七阶段流水线详细设计¶

    Stage 1 — Ingest（接入）¶

    • 输入：本地路径或 zip → 解压到独立工作副本 workspace/{audit_id}/src/（原始上传件只读留存）。
    • 语言识别：扩展名统计 + 首个可解析文件 tree-sitter 试解析双重确认。
    • 过滤：内置忽略规则（.git/ node_modules/ venv/ __pycache__/ dist/ build/ *.min.js 等）+ 解析 .gitignore + 二进制与超长文件（>10k 行）跳过并记录。
    • 输出：FileManifest（路径、语言、行数、sha256）。

    Stage 2 — Index（索引）¶

    tree-sitter 逐文件解析，写入 SQLite 四张表：

    files(path PK, language, loc, sha256, parsed_ok)
symbols(id PK, file, kind, name, line_start, line_end, signature)
-- kind ∈ {function, method, class, constant}
imports(file, module, imported_name, alias)
call_edges(caller_file, caller_symbol, callee_name, callee_file, callee_symbol, resolved)
-- resolved=1 表示跨文件精确解析成功；同文件调用不建表（直接源码可见）

    关键实现点： - 函数级 chunk：索引时同时产出"函数切片"（函数源码 + 起止行 + 签名），后续 LLM 审查以函数为单位组包，而不是整文件硬塞——这是 token 成本与上下文质量的关键。 - 跨文件调用解析：from services.user import get_user → 调用点 get_user(u) 可解析到 services/user.py:get_user；处理相对导入与 __init__.py 再导出；解析失败的调用边标记 resolved=0（仍保留，供搜索兜底）。 - 增量：files.sha256 未变 → 跳过重解析。

    Stage 3 — Understand（架构理解，map-reduce）¶

    • Map：按顶层目录分模块，每个模块把"目录树 + 模块内符号表 + 主要类/函数签名"交给 LLM，产出 200 字模块摘要。
    • Reduce：全部模块摘要 + 依赖图（Mermaid 渲染）交给 LLM，产出架构卡片：技术栈判断、分层结构、入口点、核心数据流、3~5 个"风险热点"（如上帝类、循环依赖、被 20+ 处调用的核心函数）。
    • 风险热点直接决定 Detect 阶段的资源倾斜策略（热点文件优先、预算充足）。

    Stage 4 — Detect（双通道检测，核心）¶

                    ┌──────────────────────────────┐
 源文件+切片 ──→ │ 通道A：静态规则引擎（并行，0成本）│──→ 候选集A（高召回）
                └──────────────────────────────┘
                ┌──────────────────────────────┐
 切片+符号上下文 ─→ 通道B：LLM 审查 Agent（并发8）  │──→ 候选集B（含规则hint）
   + 候选集A hint └──────────────────────────────┘
                              │
                ┌──────────────────────────────┐
                │ 验证 Agent：工具取证 + 去重合并   │
                │  · 行号真实性校验（硬校验）       │
                │  · 跨文件调用链确认             │
                │  · 同位置问题合并 source 标记    │
                └──────────────────────────────┘
                              ↓
                    结构化 Issue 列表

    通道 B 单文件审查的 prompt 组装（token 预算内动态裁剪）： 1. 架构卡片摘要（全局，~200 token） 2. 当前文件完整源码或函数切片（若文件 > 400 行，按函数切片分组审查） 3. 符号上下文：本文件调用的外部函数中，被 10+ 处调用或风险热点的函数源码（最多 3 个） 4. 通道 A 命中的规则 hint 列表 5. 输出要求：JSON 数组，每条含行号/类别/严重度/描述/置信度；没有问题就返回空数组（防硬凑）

    LLM 输出后置校验（硬规则，不过即丢或降级）： - 行号必须存在于文件且行内容与描述提到的标识符有交集； - 置信度 < 0.6 且无规则佐证 → 丢弃； - 与候选集 A 同文件 ±5 行同类问题 → 合并为一条，source=rule+llm（置信度上调）。

    Stage 5 — Fix（修复）¶

    • 目标：critical / high 全部，medium 按预算生成。
    • 每个 Issue 独立一个"修复 Agent"会话：注入 Issue 详情 + 上下文切片，产出 unified diff。
    • 应用与验证闭环：
    • git apply --check 语法校验（工作副本初始化为 git 仓库）；
    • 应用 → 重新 tree-sitter 解析该文件（语法必须可解析）；
    • 检测到项目测试框架（pytest/jest）→ 沙箱运行现有测试：全绿 → verified；失败 → 回滚 → needs-review；
    • 无测试 → 仅到第 2 步 → syntax-ok。
    • 多个 Patch 顺序应用（同文件冲突时后者标记依赖前者）。

    Stage 6 — TestGen（单测生成）¶

    • 范围：默认所有被修复函数；--tests all 时扩展到项目核心模块（Stage 3 热点优先）。
    • 每个"测试生成 Agent"输入：函数源码 + 签名 + 依赖类型 + 已修复后的版本 + 现有同类测试风格示例（如有）。
    • 产出 pytest 用例：正常路径 ≥ 2 条、边界 ≥ 2 条、异常路径 ≥ 1 条，必须含显式 assert。
    • 沙箱运行：失败则把 traceback 回喂重试 ≤ 2 次；仍失败 → 丢弃该条用例并记录原因（作为质量统计）。
    • 收录用例写入 tests/generated/test_gen_<module>.py。

    Stage 7 — Report（报告）¶

    • 聚合所有阶段产物为 report.json（schema 见 §4）。
    • Jinja2 渲染 report.md / report.html（代码高亮用 Pygments；diff 视图用 unified diff 原文）。
    • 健康分：score = max(0, 100 − (10·C + 5·H + 2·M + 0.5·L) / KLOC × 50)（系数在 bench 中用金标集标定，使典型"健康项目"落在 85+、"病态项目"落在 50 以下）。

    3. Agent 运行时设计（复用既有框架的部分）¶

    3.1 与既有框架的对接面¶

    既有工具调用框架只需满足三个接口约定（本项目的适配工作量集中在这一层）：

    class AgentRuntime:                     # 既有框架
    def register_tool(self, name, schema, handler): ...
    async def run(self, system_prompt, messages, *,
                  max_iterations: int,        # 新增：迭代熔断
                  token_budget: int,          # 新增：预算熔断
                  on_tool_call) -> AgentResult: ...

class LLMClient:                        # 新写：GLM 适配
    async def chat(self, messages, tools=None, json_mode=False) -> LLMResponse
    # 内置：信号量限流、指数退避重试×3、响应缓存(sha256(prompt+model))、token 计量

    3.2 三类 Agent 角色与停止条件¶

    角色 职责 max_iterations 停止条件
    Review Agent 单文件审查，产出候选 Issue JSON 12 输出合法 JSON / 迭代上限
    Verify Agent 对候选 Issue 工具取证，输出 确认/驳回+证据 25 结论落定 / 迭代上限（未决 → 降置信度保留）
    Fix Agent 生成 Patch 10 diff 语法通过 / 上限
    TestGen Agent 生成单测 8 沙箱通过 / 重试 2 次 / 上限

    3.3 上下文工程（面试重点）¶

    • 按需注入而非塞满：默认只给"当前文件 + 热点被调函数"，Agent 认为不够时自己调工具拿（get_symbol / find_references）——工具调用本身就是跨文件理解的执行机制。
    • 切片策略：> 400 行文件按函数分组审查，每组附"文件符号表"防断章取义。
    • anti-hallucination 约束（prompt + 代码双保险）：要求引用的行号必须来自 read_file 工具返回内容；代码层校验行号存在性，不通过即丢。
    • 结果缓存：cache_key = sha256(model + prompt)，同项目增量审计时未变文件直接命中。

    5. 并发、性能与成本设计¶

    手段 说明 预期收益
    文件级并发 asyncio + Semaphore(8) 调 GLM；tree-sitter 解析用 ProcessPool（CPU 密集） 吞吐 ×6~8
    函数切片组包 按函数而非整文件组 prompt，单请求 prompt 控制在 4~8k token token ↓40%，质量↑
    规则前置 规则零成本跑全库；LLM 预算不足时优先保证 critical/high 热点文件 预算可控
    双级缓存 LLM 响应缓存（prompt hash）+ 解析索引缓存（file hash） 增量审计 <40% 耗时
    预算熔断 全局 token 预算（默认 2M）耗尽 → 降级为"仅规则 + 已完成部分" 永不失控

    耗时模型（答辩可心算演示）：2.4 万行 ≈ 800 函数切片；并发 8、单请求平均 6s → 理论 800/8×6 ≈ 600s？——不成立，所以必须两级裁剪：① 规则无命中且非热点且 < 80 行的"低风险切片"走轻量 batch 审查（一次请求审 5 个切片）；② 热点/有命中切片才全量深审。实测目标 P50 < 30s/千行（即 2.4 万行 ≤ 12 分钟），与 US-1 剧本一致。

    6. 沙箱执行器¶

    • 实现：subprocess + 临时目录 + timeout=60s + 环境变量白名单；Windows 下先落地（creationflags=CREATE_NEW_PROCESS_GROUP 超时 kill），文档注明生产建议 Docker（--network none --memory 512m）。
    • 执行对象：项目现有测试、生成的单测、Patch 后语法解析。不执行任何来自 LLM 的任意 shell 命令（工具 run_command 仅暴露"跑 pytest/jest"白名单命令）。

    7. 技术选型清单¶

    层 选型 理由
    语言/运行时 Python 3.11 + asyncio tree-sitter/GLM SDK/pytest 生态最全；asyncio.TaskGroup 并发干净
    AST tree-sitter + tree-sitter-python/-javascript/-typescript 一套 API 多语言，增量解析快
    LLM GLM-5.3 Flash（OpenAI 兼容 Function Calling） 简历锚点；Flash 档性价比适配海量小请求
    服务 FastAPI + SSE (sse-starlette) 异步任务 + 流式进度原生支持
    存储 SQLite（索引与任务元数据）+ 文件系统（报告/patch） 零运维，单机够用
    模板 Jinja2 + Pygments 报告渲染
    测试 pytest（自身）+ BugsInPy 抽样项目（基准） 见 04 文档
    前端（演示） Vue3 + Vite 单页（或 Jinja2 服务端渲染二选一，首期推荐后者省工期） 快速出演示

    8. 关键时序（一次审计的生命周期）¶

    用户 → API: POST /api/audits {path|zip}
API → Orchestrator: 创建任务(audit_id, status=queued) → 立即返回 id
Orchestrator: Ingest → Index → Understand     [SSE: 索引进度 n/m]
            → Detect: 规则全库(秒级) → LLM 并发审查 [SSE: 审查进度/实时发现数]
            → Fix(可选) → TestGen(可选) → Report → status=done
用户 ← SSE/GET: 进度事件、最终 report.json/md/html、fix.patch、generated tests
