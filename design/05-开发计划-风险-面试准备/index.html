    05 开发计划、风险与面试准备¶

    版本：v1.0 ｜ 日期：2026-09-11

    1. 开发里程碑（6 周，每周有可演示产物）¶

    周 里程碑 关键产出 演示验收
    W1 地基 Ingest（zip/路径/过滤/编码容错）+ Index（tree-sitter 符号表/调用图/SQLite/函数切片）+ GLM Client（限流/重试/缓存）+ AgentRuntime 三接口打通 cli.py index <path> 打印符号表与调用图统计；一个最小工具循环能 read_file→回答
    W2 检测闭环 静态规则库 v1（≥ 40 条，Python）+ Review Agent（10 工具全接入）+ Verify Agent + 行号校验器 + record_issues 落库 对一个含已知 bug 的样例项目跑通"候选→验证→Issue 列表"全流程
    W3 修复与测试 Fix Agent + unified diff 生成/应用 + 沙箱执行器 + 现有测试验证 + TestGen Agent + 失败重试剔除 样例项目一处 SQL 注入：Patch 生成→沙箱验证 verified→4 条回归单测通过
    W4 报告与产品化 Understand（map-reduce 架构卡片）+ 健康分 + report.json/md/html 渲染 + FastAPI 异步任务 + SSE 进度 + Web 演示页 + JS/TS 检测支持 Web 上传 zip → 看进度 → 看报告，端到端流畅
    W5 性能与评估 并发 8 / 两级缓存 / 预算熔断 / 低风险切片 batch 审查；BugsInPy+git 历史金标标注（≥ 150 条）；bench 脚本跑通 P/R/耗时 bench 一键出指标表；耗时 P50 < 30s/KLOC 首次达标
    W6 冲刺与包装 prompt 迭代 + 消融实验 7 配置 + 效率对比实验 + README/架构图/演示视频/答辩 PPT 全指标达简历口径，留痕 run 记录

    依赖关系：W1 的 Index 是全项目咽喉（符号表质量决定跨文件能力上限），W1 超期则优先砍 JS/TS（挪到 W6 之后），绝不动摇 W2 的检测闭环。

    2. 风险清单与应对¶

    # 风险 概率/影响 应对
    R1 LLM 幻觉行号/编造问题 高/高 行号硬校验 + 置信度阈值 + Verify Agent 三道闸；prompt 首尾双写反幻觉约束
    R2 token 成本失控 中/高 函数切片组包 + 低风险切片 batch + 预算熔断降级 + 响应缓存；单项目审计前打印预估成本
    R3 tree-sitter 跨文件调用解析不准（动态分发/鸭子类型） 高/中 诚实降级：resolved=0 的边用 search_code 兜底；报告措辞区分"确认/疑似"
    R4 Windows 沙箱限制（无 namespace 隔离） 中/中 首期 subprocess+超时+白名单命令；文档注明生产用 Docker；演示在本机受控环境
    R5 Agent 死循环/工具滥用 中/中 max_iterations + token_budget + 工具调用超时 + on_tool_call 全量留痕可回放
    R6 金标标注工作量大 高/中 注入集快速起步 + BugsInPy 白捡金标 + 人工标注只做 3 个项目；两人独立+仲裁
    R7 GLM 接口限流/不稳定 中/中 指数退避×3 + 信号量限流 + 失败降级为规则结果（审计永不整体失败）
    R8 生成单测 import 崩溃率高 中/低 TestGen prompt 要求自包含 import + 沙箱预检 import 失败回喂重试

    3. 面试准备：10 个必被追问的问题与答法¶

    Q1：85% 准确率怎么测的？金标哪来的？

    答：口径是 critical/high 级别的 Precision。金标三个来源：BugsInPy 子集（自带修复 commit）、开源项目 git 历史回溯（修复 diff 反推问题位置）、3 个真实项目双人标注+仲裁，共 150+ 条。报告与金标按"同文件 + 行区间相交 + 类别一致"匹配。可以打开 bench/ 的 run 记录看原始数据，还做了 7 组消融实验——去掉 Verify Agent 后 Precision 掉到 0.68，说明提升主要来自跨文件取证而不是模型本身。

    Q2：为什么不用现成的 SonarQube / ruff / ESLint？

    答：互补而非替代。静态工具规则固定、单文件视角、误报靠人筛；我的系统把规则引擎作为高召回前置通道，LLM 负责语义判定与跨文件取证。实测 rules-only 配置在跨文件类 bug 上 Recall≈0。反过来我的系统也集成了类 ruff 规则当 hint。真正的问题是"语义级缺陷"——比如"这个函数可能返回 None"，只有读了另一个文件的实现才能确认。

    Q3：跨文件理解具体怎么实现的？

    答：三层。① 静态层：tree-sitter 全库解析建符号表 + import 解析建调用图，跨文件调用边尽力精确解析；② 上下文层：审查某个文件时自动注入它调用的热点函数源码切片；③ 行为层：Agent 对不确定的跨文件结论主动调 get_symbol/find_references 取证，Verify Agent 再独立复核一遍。核心观点：跨文件理解不是靠把所有代码塞进上下文，而是靠"索引 + 工具按需取"。

    Q4：千行 30 秒怎么做到的？瓶颈在哪？

    答：瓶颈是 LLM 网络往返。四个手段：文件级并发 8 路、函数切片组包把单请求压到 4~8k token、两级缓存（LLM 响应按 prompt hash、解析按文件 hash）、低风险切片 batch 合审。耗时模型可以现场算：2.4 万行 ≈ 800 个切片，1/3 走 batch、并发 8、均 6s/请求 → 约 11 分钟，符合 30s/KLOC。

    Q5：token 成本多少？值得吗？

    答：实测约 58k prompt + 4k completion tokens/KLOC，按 Flash 档价格约 X 元/千行（填实测值）；一个 2.4 万行项目一次全量审计约 X 元，对比 0.5~1 人日的人工初评成本，成本收益差两个数量级。增量审计靠缓存再降 60%+。

    Q6：Agent 跑飞/死循环怎么办？

    答：四层保护：单会话 25 次迭代熔断、全局 token 预算熔断（超了降级为规则结果收尾）、每个工具调用带超时、on_tool_call 事件全量留痕可回放排查。设计哲学是"审计任务允许部分结果"——预算耗尽时输出已完成部分并明确标注覆盖范围，绝不假装完整。

    Q7：生成的修复能直接信吗？

    答：分级。verified（沙箱跑通项目现有测试）> syntax-ok（无测试项目，仅语法可解析）> needs-review（验证失败已回滚）。报告里严格标注，UI 上只有 verified 是绿色。这是对 LLM 修复能力边界的诚实处理。

    Q8：生成的单元测试质量怎么保证？

    答：三道关：显式 assert 强制（禁 assert True）、沙箱跑通才收录（跑不过带 traceback 重试两次后丢弃）、抽样人工评"有效断言率"（断言值与函数语义相关）≥ 90%。丢弃率本身也是指标——它证明筛选机制在工作。

    Q9：如果代码库是 100 万行怎么办？

    答：当前单次上限 50 万行，超过走分模块审计再聚合（依赖图把模块边界切出来，跨模块问题靠符号表跨片解析）。根本设计就是 map-reduce 的：索引是 map，架构摘要是 reduce，天然可横向扩展；SQLite 换 Postgres、单机并发换任务队列即可，架构不用推倒。

    Q10：这个项目里你个人做了什么？最难的是什么？

    答（模板，按实际填）：整体设计 + Agent 编排与工具集 + 检测双通道是我做的，[合作者负责 xx]。最难的是 Verify Agent 的校准——早期它要么全确认（误报 40%+）要么全驳回（误杀真问题），解法是把"驳回也留痕"写进协议，用驳回理由数据反过来调 prompt 的判级标准，三轮迭代后稳定。这个过程让我理解 Agent 工程的核心不是 prompt 技巧，而是给模型建立可量化的反馈回路。

    4. 演示剧本（答辩/面试现场 5 分钟版）¶

    1. （30s）打开样例 Flask 项目结构，一句话讲双通道架构图。
    2. （60s）CLI 跑审计，SSE/进度条滚动，实时打印"发现 ISS-0001 critical: SQL 拼接（app/dao.py:57）"。
    3. （90s）打开 report.html：健康分、问题分布、点开那条 critical 看证据链（调用链展开），这是全场记忆点。
    4. （90s）点击生成修复：看 unified diff → 沙箱日志"14 tests passed" → verified 标记 → 自动生成的回归单测列表。
    5. （30s）收尾：展示 bench 指标表 + 消融实验图，一句话收束："规则管召回、Agent 管精确、沙箱管闭环。"
