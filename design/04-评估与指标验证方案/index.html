    04 评估与指标验证方案¶

    版本：v1.0 ｜ 日期：2026-09-11 本方案回答一个必被追问的问题：简历上 85% / 30s / 70% 三个数字是怎么测出来的。 没有本方案的数字在面试中是负债，有了才是资产。

    1. 总原则¶

    1. 每个数字对应一个可复现实验：换一个人按文档跑，能得出同一量级的结果。
    2. 口径先于数字：先定义指标公式与金标，再谈数值。
    3. 内部指标比简历更全：简历报 Precision 85%，内部同时追踪 Recall / F1 / 成本，防止"少报少错刷准确率"。

    2. Benchmark 构建（金标从哪来）¶

    2.1 数据集构成¶

    来源 数量 用途 金标获取方式
    BugsInPy 子集 10 个项目 / 50 个真实 bug Bug 检测 Recall 评估 每个条目自带"修复 commit"——修复 diff 触及的行即为金标问题位置
    开源项目 git 历史回溯 10 个活跃项目（选 500~5000 星、带测试） 综合检测 git log 筛 fix/bug/crash 类 commit ≥ 50 个，回退到引入前版本，修复 diff 反推金标
    真实项目人工标注 3 个中大型项目（合计 ≥ 8 万行） Precision 主战场 + 效率对比实验 2~3 名标注者独立通读，产出"金标问题清单"，标注分歧仲裁后入库
    规则注入集 5 个项目注入 40 个已知缺陷 快速回归（prompt 每次改动必跑） 注入即金标，100% 已知

    规模目标：金标问题 ≥ 150 条，覆盖 3 类别 × 4 严重度；其中 critical/high ≥ 60 条（Precision 主指标只在这上面算）。

    2.2 金标条目格式¶

    {
  "project": "flask-app-demo", "file": "app/services/orders.py",
  "line_start": 88, "line_end": 90,
  "category": "bug", "severity": "high",
  "description": "get_user 可能返回 None 未判空",
  "origin": "git-history | bugsinpy | manual | injected"
}

    2.3 匹配规则（报告 ↔ 金标 怎么对上）¶

    一条报告 Issue 记为"命中"金标 G，当且仅当：同文件 且 行区间与 G 相交（或相差 ≤ 3 行） 且 类别一致或更高层级一致（报告 bug 命中金标 bug/security 可放宽到 critical/high 互认，medium/low 不与 critical/high 互认）。一条金标被多条报告命中只计一次。

    3. 指标定义与计算公式¶

    3.1 检测质量¶

    Precision = 命中金标的报告数(critical+high) / 报告的 critical+high 总数      → 目标 ≥ 0.85（简历"准确率 85%"）
Recall    = 被命中的金标数(critical+high) / 金标 critical+high 总数          → 目标 ≥ 0.60
F1        = 2PR/(P+R)
误报率    = 被驳回 Issue 数 / 进入 Verify 的候选数（衡量 Verify Agent 价值）

    分层报告：按 类别 × 严重度 出 4×4 矩阵；简历只引用 critical+high 的 Precision。

    3.2 性能（千行 < 30s）¶

    耗时 = Ingest 起点至 Report 落盘的 wall time（含全部 LLM 调用与沙箱）
指标 = 耗时 / (源代码行数/1000)，对 ≥ 10 个项目分别计算后取 P50 与 P90
     → 目标 P50 < 30 s/KLOC

    注意口径诚实性：不含用户上传传输时间；沙箱验证现有测试的耗时计入（这是审计闭环的一部分）；环境写明（本机 CPU/网络/并发=8/GLM-5.3 Flash）。

    3.3 效率提升 70%（对比实验）¶

    实验设计（3 人 × 3 项目，交叉）： - 人工组：3 名有经验的开发者对 3 个项目做"初评级"代码评审（只找问题、不修复），记录耗时；产出清单与金标对齐算出人工 P/R。 - Agent 组：同一项目跑审计，记录耗时；开发者再对 Agent 报告做复核（剔除误报所需时间）。 - 对比口径：

    人工总耗时 T_human（初评）
Agent 总耗时 T_agent_end2end + 人工复核耗时 T_review
效率提升 = (T_human − (T_agent_end2end + T_review)) / T_human   → 目标 ≥ 70%

    同时报告质量对比（双方对金标的 P/R），证明"快且不更差"。若无法组织 3 人，降级口径：以 1 人 + 计时 + 报告抽样复核完成，文档如实写明样本量——诚实的小样本好过编造的大样本。

    3.4 修复与测试质量¶

    Patch 语法可用率  = git apply --check 通过数 / 生成 Patch 数          → 目标 ≥ 90%
Patch 验证通过率  = verified 数 / 进入沙箱验证数                      → 目标 ≥ 60%
Patch 人工可用率  = 抽样 30 个，人工判"可直接采纳/小改可用"比例        → 目标 ≥ 60%
单测沙箱通过率    = 收录用例通过数 / 收录用例数                        → 100%（不通过不收录）
单测有效断言率    = 抽样 30 条用例，断言语义正确（非恒真）比例          → 目标 ≥ 90%

    3.5 成本¶

    tokens/KLOC（prompt+completion 分列）、元/KLOC（按 GLM 牌价）
缓存命中率 = 缓存命中调用数 / 总调用数（增量审计场景单独报）

    4. 消融实验（Ablation，答辩最强弹药）¶

    固定金标集，逐个拆组件，证明每个设计都值钱：

    配置 拆掉什么 预期结论
    Full（完整系统） — P=0.85+，R=0.6+（基线）
    −Verify 去掉 Verify Agent，LLM 候选直接入库 Precision 显著下降（如 0.85→0.68），证明跨文件取证的价值
    −Rule hints 规则结果不注入 prompt Recall 下降 + 耗时上升（LLM 失去线索引导）
    −Symbol context 审查时不附被调函数源码 跨文件类 Bug（空指针链）大量漏报
    −Cache 关闭两级缓存 增量审计耗时回升至全量水平
    Rules-only 只跑静态规则 Precision 低（误报多）、跨文件/语义问题 R≈0
    LLM-only 只做 LLM 全量审查（无工具、无 hint） P、R 双降 + token 成本上升

    结果出一张表 + 一张柱状图放进报告与答辩 PPT。这张表是"为什么不是套壳"的直接证据。

    5. 评估流水线与记录模板¶

    bench/ 目录脚本化，一条命令出全部指标：

    python -m bench.run --dataset bench/datasets/goldset.jsonl --out bench/results/
  ├── 每个配置 × 每个项目：运行审计 → 产物入库
  ├── bench/match.py：报告-金标匹配（§2.3 规则）
  ├── bench/metrics.py：输出 metrics.json + markdown 报告表
  └── bench/ablation.py：7 个配置批量跑 + 汇总对比表

    bench/results/run_YYYYMMDD.md 记录模板：

    ## Run 2026-09-20 ｜ model=glm-5.3-flash ｜ commit=abc123 ｜ prompt_ver=v7
| 指标 | 值 | 样本量 |
|---|---|---|
| Precision (critical+high) | 0.86 | 报告 78 条 / 金标 63 条 |
| Recall (critical+high) | 0.63 | 金标 63 条 |
| 耗时 P50 / P90 | 24 / 41 s/KLOC | 12 项目 |
| Patch 人工可用率 | 0.63 | 抽样 30 |
| tokens/KLOC | 58k prompt + 4k completion | 12 项目 |
备注：prompt v7 将 severity 定义前置，medium 虚高问题缓解。

    要点：每次 prompt / 阈值改动都留 run 记录，形成调优曲线；简历与答辩引用最优一次，但能展示完整实验过程。

    6. 诚实性红线（写给自己）¶

    1. 禁止用"测试集上调到满分的注入集"冒充真实项目结果——注入集只做回归，主指标必须含真实金标。
    2. Precision 只在 critical+high 上声明（medium/low 本来就主观），且注明金标标注人数与仲裁规则。
    3. 数字全部可溯源到某次 run 记录；答不上实验细节就不要把数字写上简历。
