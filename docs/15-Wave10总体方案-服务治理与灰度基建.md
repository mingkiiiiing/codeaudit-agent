## 1. 契约 v2.1 微增（本 Wave 的行为变化，全部向后兼容）

### 1.1 F5 准入控制（server/app.py）

- 新增模块级常量（环境变量可覆盖，便于测试与部署调参）：
  - `_MAX_RUNNING_AUDITS`：同时运行中的任务上限，默认 **4**（env `CODEAUDIT_MAX_RUNNING`，≥1）；
  - `_MAX_PENDING_AUDITS`：非终态（queued+running）任务总数上限，默认 **20**
    （env `CODEAUDIT_MAX_PENDING`，≥ `_MAX_RUNNING_AUDITS`）。
- 调度语义：后台任务经全局 `asyncio.Semaphore(_MAX_RUNNING_AUDITS)` 排队执行；
  超出 semaphore 的任务停留既有契约状态 **queued**（v2 状态机天然支持，无新状态）。
- 拒绝语义：POST `/api/audits` 与 POST `/api/audits/upload` 在建任务前检查
  `active ≥ _MAX_PENDING_AUDITS` → **429**，detail=`服务器并发审计数已达上限（N），请稍后重试`。
  契约 v2.0 的 200/400/404/413 全部不变，仅新增 429 一个可能响应码。
- 取消语义不变：排队中的任务被 DELETE → `task.cancel()` 令 semaphore acquire 抛
  CancelledError → 既有 BaseException 兜底落 failed + 「任务已取消」。
- 健康检查 `/api/health` 的 `audits.active/total` 语义不变（active 本就含 queued）。

### 1.2 F2 流式上传（server/app.py）

- `upload_audit` 改为分块读取（256 KB chunk 累计计数），累计超过 `_UPLOAD_MAX_BYTES`
  立即返回 413 并停止读取剩余 body——不再把整个文件缓冲进内存。
- 200/400/413 的语义与既有一致；落盘字节与请求体逐字节一致（既有用例
  `test_upload_zip_creates_audit_and_persists_file` 不变即契约）。

### 1.3 F4 沙箱输出限量（audit/sandbox/executor.py）

- `_drain` 改为限量排空：累计读取达 `_OUTPUT_LIMIT_BYTES`（默认 **8 MB**）后继续读但
  **丢弃**（防止子进程 PIPE 写阻塞），内存占用上限 ≈ LIMIT + 一个 chunk。
- `SandboxResult` 新增可选字段 `truncated: bool = False`（默认值，向后兼容）：
  输出被限量时置 True，且 `stdout_tail/stderr_tail` 首行追加 `[output truncated]` 标记。
- `run()/run_tests()` 签名与返回语义不变；既有用例（tail 80 行、超时击杀、白名单）全部不变。

### 3.1 集成裁决记录（收口期两处口径修正，均为测量口径而非行为放宽）

- **A6 RSS 校验改增量口径**：`PeakWorkingSetSize` 是进程生命周期峰值，A1–A5 场景已将其
  推高（W9/W10 两代均为 660MB 佐证峰值与上传无关），不能作为单次上传的内存证据。
  改为上传前后**当前工作集增量** < 50MB（W9 基线增量 3.3MB）；峰值仅记录为参考。
- **soak RSS 判定改三态**（PASS / DEFER / FAIL）：冷启动预热（前 60s 懒加载导入）剔除后，
  稳态斜率 < 1 MB/min → PASS；超限但 RSS 与累计终态任务数 Pearson r ≥ 0.6 → **DEFER**
  （疑似每任务常数缓存而非时间泄漏；FIFO 容量 50 兜底下内存有界 ≈ 基线 + 50×每任务增量，
  实测 ~0.15 MB/任务；不阻断发布，长窗口归因列 W11 待办）；超限且与任务数弱相关 → FAIL
  （时间泄漏特征）。quick 冒烟与标准 300s 同口径；全窗口斜率与相关性继续在报告「RSS 诊断」
  节如实呈现。
