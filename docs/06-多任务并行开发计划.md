# 06 多任务并行开发计划

版本：v1.0 ｜ 日期：2026-09-11
本文档是并行开发的"施工总纲"：任务怎么分、边界在哪、接口冻结成什么样、怎么合入。
**核心原则：契约先行（T1 冻结接口）→ 目录所有权隔离（零文件冲突）→ 各任务自带测试 → 主控集成验收。**

---

## 1. 分工总览（6 个大任务）

| 代号 | 任务名 | 范围 | 拥有目录（独占写权限） | 前置 | 波次 |
|---|---|---|---|---|---|
| **T1** | 契约层与项目骨架 | 数据模型、配置、协议接口、公共工具、样例工程 | `audit/models.py` `audit/config.py` `audit/workspace.py` `audit/pipeline.py` `audit/errors.py` `audit/utils.py` `audit/llm/base.py` `audit/agent/base.py` `audit/indexer/base.py` `audit/detect/base.py` `tests/samples/**` `tests/conftest.py` `pyproject.toml` | 无 | **W0（先行，其他人的开工前提）** |
| **T2** | 接入与索引 | Stage1 Ingest + Stage2 Index（tree-sitter 符号表/调用图/SQLite/函数切片） | `audit/ingest/**` `audit/indexer/**`（base.py 除外） `tests/unit/ingest/**` `tests/unit/indexer/**` | T1 | Wave 1 |
| **T3** | LLM 基建与 Agent 运行时 | GLM 客户端、Agent 循环、10 个工具、沙箱、Review/Verify 角色实现 | `audit/llm/**`（base.py 除外） `audit/agent/**`（base.py 除外） `audit/agents/**` `audit/sandbox/**` `tests/unit/llm/**` `tests/unit/agent/**` `tests/unit/sandbox/**` `tests/unit/agents/**` | T1 | Wave 1 |

**集成人**：主控（T1 承担者）。T5 的 Orchestrator 在各包就位后由集成人联调（T5 交付时用桩或最小实现保证自身测试通过）。

## 2. 协作规约（并行不冲突的五条铁律）

1. **契约冻结**：T1 交付的 10 个契约文件是唯一接口真相。任何任务**不得修改**契约文件；发现契约缺陷 → 在交付报告里记"接口变更申请"，由集成人统一改版（v1.1）并通知全员。
2. **目录所有权**：只在自己拥有的目录里创建/修改文件。公共文件（`pyproject.toml`、`conftest.py`、样例工程）只读。需要新依赖 → 报告给集成人，**不自行改 pyproject**。
3. **依赖冻结**：只能使用 pyproject 已声明依赖（tree-sitter 系、httpx、fastapi、uvicorn、sse-starlette、jinja2、pygments、charset-normalizer、pytest、pytest-asyncio）+ 标准库。
4. **测试自证**：每个任务交付时 `python -m pytest tests/unit/<自己的包> -q` 必须全绿。**测试禁止任何网络调用与真实 LLM 调用**——LLM 一律用 `audit.llm.base.FakeLLMClient`（脚本化回放）。
5. **交接物**：每个任务交付一份结构化报告：创建的文件清单 / 对外 API 签名 / 测试命令与结果尾部 / 与契约的偏差 / 给集成人的备注。

## 3. 依赖关系

```
T1 契约层 ──┬──> T2 接入与索引 ──────────┐
            ├──> T3 LLM基建/Agent运行时 ──┼──> 集成（主控联调 Orchestrator 全链路）
            ├──> T4 理解与检测 ───────────┤
            ├──> T5 报告与产品化（先桩后联）─┤
            └──> T6 评估 Bench ───────────┘
```

T2/T3/T4/T6 相互零依赖、完全并行；T5 只依赖 T1 契约（用桩开发），集成阶段由主控接上 T2/T3/T4 的真实实现。

## 4. 契约清单（T1 冻结，各任务 import 这些）

| 契约文件 | 冻结内容 | 主要使用方 |
|---|---|---|
| `audit/models.py` | 枚举（Severity/Category/FixStatus…）与全部数据类（FileManifest/Symbol/FunctionSlice/RuleHit/Issue/Patch/TestCase/ArchitectureCard/AuditReport…），均带 `to_dict()/from_dict()` | 全员 |
| `audit/config.py` | `AuditConfig` + `from_env()`（GLM_API_KEY/GLM_BASE_URL/GLM_MODEL） | 全员 |
| `audit/workspace.py` | `WorkspaceContext`（工作副本根、DB 路径、带行号读文件、遍历源文件） | T2/T3/T4 |
| `audit/llm/base.py` | `LLMClient` 协议、`LLMResponse`/`ToolCall`、`FakeLLMClient`（脚本回放+调用录制） | T3/T4/T5 |
| `audit/agent/base.py` | `ToolSpec`/`AgentLimits`/`AgentResult`/`AgentRuntime` 抽象基类 | T3 |
| `audit/indexer/base.py` | `IndexStore` 协议（build/symbols/get_symbol/references/call_chain/dependencies/slices/stats） | T2 实现；T3/T4 消费 |
| `audit/detect/base.py` | `RuleContext`、`Rule` 抽象基类、`RuleRegistry` | T4 实现；检测流水线消费 |
| `audit/pipeline.py` | `PipelineContext`（config/workspace/llm/emitter/各阶段产物容器）、`EventEmitter` 协议 | T4/T5 |
| `audit/errors.py` / `audit/utils.py` | 异常层级 / 哈希、行截断、ID 生成等工具函数 | 全员 |

关键跨任务调用约定（集成协议）：
- T2 暴露：`ingest(source, work_root) -> WorkspaceContext`、`create_index(workspace, db_path=None) -> IndexStore`。
- T3 暴露：`GlmClient(LLMClient)`、`SimpleAgentRuntime(AgentRuntime)`、`build_default_tools(workspace, index, sandbox) -> list[ToolSpec]`、`SandboxExecutor`、`review_file(...) -> list[Issue]`、`verify_issue(...) -> Issue`。
- T4 暴露：`run_rules(ctx) -> list[RuleHit]`、`build_architecture(ctx) -> ArchitectureCard`、`hits_to_issues()/dedup()/validate_line()`、`run_detection(ctx, review_fn=None) -> list[Issue]`（`review_fn` 由集成时注入 T3 的 review_file，缺省纯规则模式）。
- T5 暴露：`build_report(ctx) -> AuditReport`、`render_markdown/html(report) -> str`、`run_audit(config, emitter) -> AuditReport`、FastAPI app、`cli.py`。

## 5. 各任务验收标准（DoD）

- **T1**：`import audit` 可用；契约层自身单测（模型序列化回环、FakeLLM 回放、utils）全绿；`tests/samples/demo_proj` 含 ≥10 个可被规则命中的已知缺陷。
- **T2**：对 demo_proj 建立 SQLite 索引：符号/导入/跨文件调用边（resolved 标记）/函数切片可查询；文件未变时二次 build 零重解析；zip 与目录两种入口产出一致；GBK/UTF-8 容错。
- **T3**：FakeLLM 驱动下：Agent 循环可完成"工具调用→结果回填→record_issues 收尾"；25 次迭代熔断生效；GLM 客户端单测全 mock（限流信号量、指数退避、响应缓存、token 计量）；沙箱超时 kill 生效；10 个工具的 JSON Schema 与 docs/03 §2 一致。
- **T4**：≥25 条 Python 规则各带正反用例；行号校验器能拦截伪造行号；hint 注入与 (file, category, ±5行) 去重正确；无 LLM 时纯规则模式可独立产出 Issue。
- **T5**：demo_proj 端到端（FakeLLM/纯规则）产出 report.json + report.md + report.html；健康分公式与 docs/02 §2 一致；API 创建任务→SSE 进度→取报告 全链路测试通过；CLI `run/index` 可用。
- **T6**：matcher 按 docs/04 §2.3 规则命中判定（同文件+行相交±3+类别一致）单测通过；P/R/F1、耗时分位、成本计算对合成数据输出正确；`python -m bench.run --help` 可执行。

## 6. 波次计划

- **Wave 0（T1）**：契约层 + 骨架 + 依赖安装，全体开工前提。
- **Wave 1（T2~T6 并行）**：五个任务包并行开发，交付后主控集成：接线 Orchestrator → 全量 pytest → `cli.py run tests/samples/demo_proj` 冒烟 → 修复跨包问题。
- **Wave 2（集成后）**：Fix/TestGen Agent 端到端（Stage5/6）、JS/TS 规则扩充、真实 GLM 联调与 prompt 调优、金标标注与 bench 实测、演示打磨（对应总计划 W3~W6）。

## 7. 并行开发特有的风险与对策

| 风险 | 对策 |
|---|---|
| 契约理解偏差导致集成对不上 | 契约文件即代码（可 import 可测试），不留纯文字接口；集成人跑全量测试兜底 |
| 各任务悄悄引入不同依赖版本 | 依赖冻结清单 + 集成人统一管 pyproject |
| 测试互相干扰（端口/临时目录/时间） | 禁固定端口（测试用 ASGITransport/TestClient）、强制 tmp_path、无网络 |
| 包间循环 import | 依赖方向单向：models/utils ← 一切；pipeline 只依赖 models/base 契约；业务包之间通过集成注入（如 review_fn）而非直接 import |
